Findings

High The wall builds a second, older schedule

functions/src/wallState.ts

Gage’s redesigned week is saved in weeklyTemplates. desktop/src/lib/writeTemplate.ts leaves the old template array in place on purpose, and says it is ignored once weeklyTemplates.G exists.

The phone (personTemplate in public/index.html), the Mac, and nucleusAI (shared/state.ts selfShiftId and buildShiftMap) all read the new field. getWallState still walks state.template, state.alt, overrides, overtime, and partner.shifts. It never mentions weeklyTemplates, dependents, or pending.

After a normal template edit in Nucleus Manager, the wall can show Gage’s old week, skip Kaylene’s weekly pattern and Daisy’s classes, and treat an unapproved photo import as a real shift.

Fix. Build the wall’s day list from buildShiftMap. Skip rows with pending: true.

High The guest link names the household

public/index.html buildPublicShareSnapshot · desktop/src/lib/publicShare.ts

share.html and the ICS feed only need the sanitized days: who, shift name, start, end, and event titles. Both publishers also write ownerUid and householdId into publicShares/{token}. The rule is allow read: if true. Firestore rules cannot hide individual fields, so anyone with the link learns both ids.

Email and password sign-in is enabled, so a visitor can create a Firebase account and then use that id. The rest of the rules treat a household id as unguessable.

Fix. Keep the public doc to the sanitized calendar. Store ownership in a member-only document, and point the update and delete rules at that.

High Push-token writes skip membership

firestore.rules · match /households/{householdId}/pushTokens/{tokenDocId}

Create, update, and delete succeed when the document id equals the caller’s uid. The rule does not check memberUids, and it does not constrain role. Read does check membership, so an outsider cannot list existing tokens. They can add their own.

tokensForRoles in functions/src/index.ts sends to every token doc whose role is in the target list. A new document with role: "admin" receives admin and partner notifications: coverage replies and schedule changes.

The attacker cannot overwrite Gage’s token. The document id has to be their own uid. The attack adds a recipient.

Fix. Require the caller to be in memberUids, and only allow role to equal their role on the household document.

High Wall photos are listable and deletable by any account

storage.rules · match /wallPhotos/{householdId}/{photoId}

allow read: if true covers both get and list. Create and update require a signed-in user, an image, and a file under 10 MB. Delete requires only a signed-in user. There is no household check.

The comment in the file says the membership check was removed because a cross-service firestore.get() was denying real uploads. The Firestore mirror at households/{id}/wallPhotos is still member-gated, and that is what getWallState lists. A stranger cannot add a photo to the slideshow. With the household id from the share link, they can list, download, and delete the files already in the bucket. Persistent download URLs then 404.

Fix. Put the membership check back on write and delete, or stop using the household id as the object path. Public read of a single unguessable URL can stay, since that is how the wall page loads a photo.

Medium A wall link can reboot the Pi

functions/src/piCommand.ts · firestore.rules wallTokens

sendPiCommand authenticates with a wallTokens document, not a user session. The allowed set includes reboot, restart_kiosk, and toggle_kiosk. open_playlist also accepts an unsanitized args object.

Any member can create a wall token, including a supporting caregiver. The meta rules block caregivers from writing piCommand directly, and tests/rules.test.mjs covers that. This HTTPS function uses the Admin SDK and bypasses those rules. The comment in piCommand.ts says sharing the wall token with control commands does not widen the trust model. It does: the token was a read capability, and it is now a reboot capability, and a caregiver can mint it.

Fix. Drop reboot, restart, and kiosk toggles from the token-authenticated set, or require a separate control token that only an admin or partner can create.

Medium Production is still one document, last write wins

public/index.html saveStateToFirestore · docs/data-model.md

docs/data-model.md is accurate. The per-record model, the legacy bridge, and the rules tests are built. No household has schemaVersion 2, so nothing in production reads those records yet.

While a household is unmigrated, the phone does ref.set of the entire in-memory state, debounced 300 ms. There is no transaction. A stale phone overwrites a Mac edit. Photo imports are stored inline as data URLs on state.imports, inside the same document, toward Firestore’s 1 MB cap.

A new top-level field has to be added to mergeStateFromFirestore or the next phone save deletes it. scripts/contract-check.mjs is what currently catches that. The merge also warns in the console when Firestore holds a key the phone does not know.

Fix. This is a data move, not a drive-by. Do it when you are ready to migrate the household. Until then, do not store new large blobs in state/main.

Medium cleanSchedule has no size cap and no role check

functions/src/cleanSchedule.ts · functions/src/parseSchedule.ts · functions/src/askClaude.ts

parseSchedule refuses a supporting caregiver and rejects a base64 payload over about 7.5 million characters. cleanSchedule checks that the caller is signed in and belongs to a household, then sends the image to Claude with no size cap and no role check. A caregiver account can call it.

askClaude blocks caregivers and withholds write tools in read mode, which is the right shape. It also accepts the client’s full conversation history with no length cap and will run up to six model rounds. None of the Anthropic callables are rate-limited per uid.

Fix. Give cleanSchedule the same cap and the same admin-or-partner check. Cap askClaude history to a fixed number of recent turns.

Low BRIDGE.md describes rules that no longer exist

BRIDGE.md — last updated 2026-05-09

The doc says any member can write state/main, a partner has the same write access as an admin at the rules layer, and any signed-in user can create an invite code. The live rules are tighter: state writes are admin or partner and only while schemaVersion is under 2, invite codes can be created only by an admin or partner of the named household and cannot grant admin, and codes cannot be listed.

The next desktop or second client written from this doc will fight the rules.

Fix. Rewrite the security section from firestore.rules, or mark the file historical and point readers at docs/data-model.md.

Low Photo import’s “today” ignores the household time zone

functions/src/parseSchedule.ts isoToday

isoToday is hardcoded to America/New_York and that date is handed to Claude as “today” so it can infer the year on a photographed schedule. The household already stores timeZone. The health-calendar sync uses the caller’s zone. A photo taken near midnight can be dated a day off, and a year boundary can land on the wrong year.

Fix. Read timeZone off the household and use it in isoToday. Fall back to New York only when the field is missing.

Low Several Family Console controls do not save

desktop/src/components/FamilyConsole.tsx

Remove Daisy, feed edit, the monthly limit, and the connector cards are local placeholders. The click handlers are empty, marked TODO. They look like settings. Email delivery for invites is also unwired.

Fix. Hide the controls until they write, or wire them. Do not leave a control that appears to save.

What the guest link unlocks

The sanitized calendar itself is the right idea. Shifts and event titles go out. Emails, chat, coverage notes, health, and pay do not. The leak is the two ids sitting next to that calendar, plus two rules that assumed the household id would stay private.

  1. Read publicShares/{token} with no account. Learn householdId and the owner’s uid.
  2. Sign in with any Firebase account. Write households/{id}/pushTokens/{yourUid} with role: "admin" and your own FCM token. Membership is not checked.
  3. List wallPhotos/{householdId}/. Download or delete the objects. The slideshow doc in Firestore stays member-only, so the wall does not start showing an uploaded replacement. Existing photos break when the bytes are deleted.

The rewrite that is waiting

The any-household model in docs/data-model.md is the real fix for last-write-wins, the 1 MB document, and caregiver access to the whole schedule. People, shifts, events, and coverage each become their own document. shared/store.ts, shared/toLegacy.ts, the function-side editLegacyState, and tests/rules.test.mjs are already there. schemaVersion on the household root is the switch. Nothing has been switched.

Until a household is migrated, every new surface has to re-derive the schedule from the legacy shape. nucleusAI was moved onto shared/state.ts after an earlier copy drifted and answered with a calendar the Mac disagreed with. The wall is the copy that was not moved.

nucleusAI’s system prompt is still this household: Gage, Kaylene, and Daisy by name, with Daisy described as the supporting caregiver. That matches how this family actually uses the app. It will be wrong for a household the new model is meant to represent. Not a daily bug. Do not “generalize” the prompt until a second household exists.

Leave these alone

The rules have been tightened with care, and the tests cover the cases that used to be open:

  • A stranger can no longer overwrite or delete someone else’s share by stamping their own uid. Update and delete check the existing household.
  • A supporting member cannot post chat as “Manager” or set fromManager and toUids.
  • Caregivers cannot write state/main. Their changes go through caregiverAction.
  • Invite codes can be fetched by id and cannot be listed. Creating one requires admin or partner of that household, and the code cannot grant admin.
  • Direct client writes to meta/piCommand are denied. The hole is the HTTPS function, not this rule.
  • nucleusAI writes go through the shared schedule module, and undo refuses when those fields have changed since the edit.
  • The Anthropic and Google keys are function secrets, not bundle constants. The Firebase web apiKey in BRIDGE.md is a public identifier. Access is the rules.
  • mergeStateFromFirestore warns when it sees a top-level key it would drop on the next save.

Do these first

  1. Take householdId and ownerUid out of the world-readable share doc. Keep ownership in a member-only document.
  2. Require household membership on pushTokens writes, and only allow the caller’s real role. Restore a membership check on wall-photo writes and deletes, or stop using a guessable household id in the object path.
  3. Point getWallState at buildShiftMap. Skip rows with pending. Drop reboot from the token-authenticated command list, and stop letting a supporting member mint a control token.
  4. Give cleanSchedule the same image cap and admin-or-partner check parseSchedule already has. Cap askClaude history length.

Migrating the household is the real fix for last-write-wins and the 1 MB document. It is a data move. The four items above are safe while the household stays on state/main.
